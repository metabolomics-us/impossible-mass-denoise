Connect an agent

The same cleaner this page uses is available as a Model Context Protocol server, so an agent — Claude, Cursor, Copilot, pi, or your own script — can clean your spectra and, unlike a REST call, tell you why each ion went away. Nothing is uploaded anywhere by the agent: the tools read the spectrum you hand them and return the answer.

  • Streamable HTTP, no key needed
  • Every removal carries a reason
  • Same tables and verdicts as the web page

1 Point your client at the endpoint

The MCP endpoint is Streamable HTTP at

https://denoise.mcp.metabolomics.us/mcp

There is no key, token or login: the tools only report on a spectrum you send them, and the server holds nothing between calls (it is stateless, so a restart costs a client one retried request). If the address refuses to connect, the release is not deployed yet — step 2 works regardless.

Most clients take the same shape — a name and a URL. In Claude Desktop, Claude Code (.mcp.json), Cursor or VS Code:

{
  "mcpServers": {
    "denoise": {
      "type": "http",
      "url": "https://denoise.mcp.metabolomics.us/mcp"
    }
  }
}

In pi, from a shell:

pi mcp add denoise --url https://denoise.mcp.metabolomics.us/mcp

Then ask for what you would normally do by hand: clean spectrum.msp and tell me what you removed and why, or is 100.5 a real ion in positive mode? The agent picks the tool; you get the reasons back.

2 Or run it beside your own data

Same code, no network: the server speaks MCP over a pipe (stdio) and reads the tables from the repository checkout. The MCP SDK needs Python 3.10 or newer, which is why this runs in its own environment instead of the one the REST service uses.

git clone git@github.com:metabolomics-us/impossible-mass-denoise.git
cd impossible-mass-denoise
python3.12 -m venv .venv-mcp
.venv-mcp/bin/pip install -r requirements.txt -r requirements-mcp.lock

.venv-mcp/bin/python -m denoise_mcp --stdio

Configure that as a stdio server instead of a URL:

{
  "mcpServers": {
    "denoise": {
      "command": "/path/to/impossible-mass-denoise/.venv-mcp/bin/python",
      "args": ["-B", "-m", "denoise_mcp", "--stdio"]
    }
  }
}

Add --expect-fingerprint <hex> to refuse to start on chemistry tables other than the ones you checked, and --host 127.0.0.1 --port 8301 --allowed-host <name> to serve HTTP yourself (the allowlist is what stops a page on another domain from reaching a local port).

What a call returns

An agent reads an answer, not a stream of bytes, so the default answer is the part that fits and matters: counts first, then the removed ions with their reasons. The clean peak list is opt-in, because on a 5 000-peak spectrum it is the biggest thing in the reply and the least interesting part.

{
  "summary": {
    "mode": "pos", "halogens": false,
    "labels": { "deuterium": 0, "carbon13": 0, "nitrogen15": 0 },
    "precursor_mz": null,
    "fingerprint": "5aae4ec26694da4d", "table_max_mz": 1700.0,
    "total": 4, "kept": 2, "removed": 2,
    "intensity_in": 165.0, "intensity_removed": 25.0,
    "intensity_removed_fraction": 0.15151515151515152,
    "removed_above_table": 0, "formulas_computed": 0, "formulas_skipped": 0
  },
  "removed": [
    { "mz": 100.5, "intensity": 20.0,
      "reasons": ["nearest-legal-below", "possible-as-doubly-charged"],
      "narrative": "m/z 100.5000 (positive polarity); the closest allowed mass is
                    100.1247, below this ion by 375.3 mDa; explainable as a doubly
                    charged ion (z=2); the deployed model assumes z=1.",
      "nearest_legal_mz": 100.12465194171052, "nearest_legal_mDa": -375.34805828947526 },
    { "mz": 123.9, "intensity": 5.0,
      "reasons": ["nearest-legal-below", "legal-within-10mDa", "needs-halogen-alphabet"],
      "narrative": "m/z 123.9000 (positive polarity); the closest allowed mass is
                    123.8945, below this ion by 5.5 mDa; an allowed mass exists within
                    10 mDa, so this ion falls in a gap that makes the model discriminating
                    rather than broken; it needs a halogen (Cl, F, Br or I) to be
                    explainable, and this request did not allow the halogen alphabet.",
      "nearest_legal_mz": 123.89449747463188, "nearest_legal_mDa": -5.502525368129341 }
  ],
  "kept": null,
  "kept_omitted": "include_kept=true would add 2 peaks (~74 bytes as JSON)",
  "kept_truncated": null,
  "removed_truncated": null,
  "answer_bytes": 1438,
  "answer_oversized": null
}

That is the answer to the four peaks in the curl example below — copied, not written by hand. The fields that exist to keep an agent honest about what it is looking at:

  • kept_omitted names the option that adds the surviving peaks and says how big the answer would get, so a caller can ask only when it needs the list.
  • removed_truncated is null unless the removals were cut to fit, in which case it says how many were returned, in what order, and how to read the rest. The counts in summary always cover the whole spectrum, and an answer is never quietly shortened.
  • kept_truncated is the same promise for the peak list a caller asked for with include_kept=true: when the answer has to be fitted to max_answer_bytes, it says how many of the surviving peaks arrived.
  • answer_oversized is the last resort, for an answer that cannot be fitted at all because the summary alone is too big. It is stated rather than left for a harness to cut.
  • answer_bytes says how big this answer is as it goes out, against the max_answer_bytes budget — so a caller can see how much of its reading room one call took, and ask for less next time.
  • fingerprint identifies the chemistry tables that made the verdict and table_max_mz the mass they were built up to.

A clean_batch answer is the same idea at batch scale: a summary over every spectrum, then one per_spectrum summary each in the order sent. Removals are not repeated there — they arrive as progress lines while the batch runs — and the same answer_bytes and answer_oversized pair applies to the whole reply, because 200 summaries on their own already outrun the budget.

Tools

ToolUse it forCost
clean_spectrumOne spectrum, up to 5 000 peaks. Returns summary + removals.Fast; explanations add a little work per removed ion.
clean_batchUp to 200 spectra in one call. Stops on the first spectrum that breaks its limits and says which one.Linear in spectra; stream: true keeps you informed while it runs.
explain_ionOne m/z: is it possible, why not, and how far to the nearest legal mass.Cheap; model_flags: true (which validity model accepts it) is about 200× dearer.
service_infoTables loaded, fingerprint, ceiling, every limit that will reject a request.Read this before a large request.

Beyond the peaks, four options change the answer rather than the work: halogens (widen the alphabet to F/Cl/Br/I, which rejects fewer noise peaks), precursor_mz (keep the precursor whatever the filter makes of it), deuterium / carbon13 / nitrogen15 (declare a labelled standard’s label count so its ions are kept), and explanations: false (verdicts without the why). Two more cost real work and are capped per call: formulas (a formula witness for kept peaks, about 500× a verdict) and model_flags (which validity model kept each peak, about 200×). nearest_only trades the reason list for just the distance.

Progress while it works

Ask for stream: true and the server pushes notifications while the cleaning runs, so an agent sees lines arriving instead of one long silence: KEPT 181.0707 100.0, REMOVED 100.5000 20.0 nearest-legal-below|possible-as-doubly-charged, and SPECTRUM index=41 total=200 kept=18 removed=3 as each spectrum in a batch finishes. clean_batch streams by default; clean_spectrum does not. By default every line is sent — pass min_progress_interval_ms to thin the per-peak lines on a big spectrum (a finished spectrum is always reported), and explanations: false in a batch leaves only the per-spectrum lines.

Limits, and why they exist

An agent’s context window is the reason for the odd ones. Harnesses cut a long tool reply without saying so, and a cut-off peak list is worse than no list: so the answer is measured, fitted, and made to report what it gave up. Counting entries is not enough by itself — 250 removals that each carry a measured sentence measured 120 KB — which is why there is a byte limit as well as a count limit.

LimitValueWhy
Peaks per spectrum5000Above this, use the web page or REST, which stream to a file.
Spectra per batch call200Keeps one call inside a client’s patience.
Removed peaks listed250Beyond it the reply is cut to this many, and removed_truncated says so.
Answer size20000 bytesWhat an agent harness reads whole before cutting the rest in silence. A bigger answer is fitted to it — the sentences on tail removals first, then the opted-in peak list, then whole entries — and says which of those it gave up.
Formula lookups per request200000Bounded work per request, so one caller cannot hold the server.
Formula ions explained per call50Full formula hypotheses are the expensive part.
Model ions per call50The validity models cost about 200× a verdict.
Explanation work per call1000000 µsStops, with a clear message, instead of running unbounded.
Label count12Enough for any labelled standard people actually run.
Mass ceiling1700 m/zThe tables stop there; above it every ion is reported possible.

Exact values come from service_info, which reports the limits the running server will enforce; this table is written for people.

By hand, without a client

The transport is JSON-RPC 2.0 over HTTP POST. Two headers matter: Accept must name both application/json and text/event-stream, or the server answers 406; and every request needs an id to get an answer back (without one it is a notification and you get 202 with nothing).

curl -sS https://denoise.mcp.metabolomics.us/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
        "name":"clean_spectrum",
        "arguments":{"mode":"pos",
                     "peaks":[[181.0707,100],[100.5,20],[123.9,5],[85.0284,40]]}}}'

The reply arrives as one event: message SSE frame whose data: line holds the JSON-RPC answer — the summary above, with 181.0707 and 85.0284 kept and 100.5 and 123.9 removed. List the tools with {"method":"tools/list","params":{}} and the reason codes with {"method":"resources/read","params":{"uri":"denoise://reason-codes"}}.

Trouble
  • 406 — the Accept header is missing text/event-stream.
  • 421 — the Host the server saw is not the name it was started for; a proxy must forward the public name.
  • 413 / 422 — the body or the request broke a limit named in the message; fix the request, do not retry it.
  • A tool answer with isError — a limit or a bad argument, stated in plain words; this is an ordinary answer, not a protocol failure.
  • Nothing on / — the MCP host serves only /mcp; the web page and REST API are on denoise.metabolomics.us.

Same cleaner, two doors

  1. One implementation. The MCP tools call the same classifier the web page and the REST API call, so a verdict cannot differ by door.
  2. Proven equal. A release test sends the identical peaks down both doors and fails if any verdict differs, and checks that the reason codes the tools emit are the ones this page lists.
  3. Nothing invented. Explanations stop at the mass the tables were built to. Above 1700 m/z the answer is “possible”, and the tool says so rather than guessing.
What does “impossible” mean?

Impossible means not explained by CHNOPS, singly charged, monoisotopic. Works for Orbitrap data; off by default for TTOF; not for QTOF. Ions above 1700 m/z are always reported possible.

Prefer plain HTTP? The REST API takes the same spectra and returns the same verdicts, and this site’s form needs no setup at all.
